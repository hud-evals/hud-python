An **agent** is what acts inside an [environment](/v6/reference/environment): it works a
[task](/v6/reference/tasks) through the environment's [capabilities](/v6/reference/capabilities) and produces the
answer that gets graded. Concretely it's a **model** wrapped in a **harness** - the loop that feeds the
model observations and turns its output into actions. In the framework an agent is anything callable as
`await agent(run)`, where the `run` is the live handle for one task: its prompt, its connection to the
environment, and the trace it fills.

Because an environment only exposes capabilities, the agent isn't baked in - use a built-in agent for a
standard model, or [bring your own harness](/v6/advanced/extending#bring-your-own-harness) for a custom
loop.

## Built-in agents

The SDK's agents run a coding agent's own CLI inside the environment's workspace:

| Agent | Runs | Config | Default model |
|-------|------|--------|---------------|
| `ClaudeCLIAgent` | Claude Code (`claude`) | `ClaudeCLIConfig` | `claude-haiku-5-5` |
| `CodexCLIAgent` | Codex (`codex exec`) | `CodexCLIConfig` | `gpt-6-luna` |
| `PiAgent` | [Pi](https://pi.dev) (`pi --mode json`) | `PiConfig` | `deepseek/deepseek-v4.1-flash` |

```python
from hud.agents import create_agent

agent = create_agent("claude_cli")
```

Each config lives in `hud.agents.types`, and every setting (`model`, `timeout_seconds`,
`reasoning_effort`, ...) lives on it; `__call__(run)` takes only the run. `timeout_seconds` bounds the
whole run.

`PiAgent` is the harness for open and other OpenAI-compatible models: Pi calls its model over Chat
Completions, through the HUD gateway with `HUD_API_KEY`, or at `OPENAI_BASE_URL` (default
`https://api.openai.com/v1`) with `OPENAI_API_KEY`. It always needs one of those, since it ignores
any Pi login in the workspace. The environment's MCP servers reach it as Pi tools; Pi speaks only
streamable HTTP to them, so an `sse` or `websocket` MCP capability fails the run. It needs a POSIX
workspace. Computer use over an `rfb` capability needs a model that reads images:
`model_info={"input": ["text", "image"]}`.

```python
agent = create_agent("pi")
```

`PiConfig.extensions` loads your own [Pi extensions](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/extensions.md) into the run. It
maps a file name (`*.ts` or `*.js`) to the extension's source, and Pi loads each one as it does
extensions in its own config directory. An extension can register tools and hook Pi's events, such as
`tool_call`, `tool_result` and `before_provider_request`. It can import the packages Pi provides
(`@earendil-works/pi-coding-agent`, `typebox`, ...), but not npm dependencies of its own. Extensions
an environment ships in its workspace's `.pi/extensions` load too. This one gives every `bash` call a
two-minute timeout unless the model sets its own:

```python
BASH_TIMEOUT = """
import { isToolCallEventType, type ExtensionAPI } from "@earendil-works/pi-coding-agent";

export default function (pi: ExtensionAPI) {
  pi.on("tool_call", (event) => {
    if (isToolCallEventType("bash", event)) event.input.timeout ??= 120;
  });
}
"""

agent = PiAgent(PiConfig(extensions={"bash-timeout.ts": BASH_TIMEOUT}))
```

A hook that changes a tool's input changes what runs, while the trace keeps the arguments the model
sent.

The SDK also ships HUD's older [provider agents](#provider-agents), which are deprecated.

### What a CLI agent needs

- **A workspace.** The agent runs its CLI over the environment's `ssh` capability, against the
  workspace filesystem. POSIX and Windows workspaces both work for Claude Code and Codex; `PiAgent`,
  and computer use over an `rfb` capability, need a POSIX workspace.
- **The CLI.** `claude`, `codex` or `pi` must be installed in the workspace, unless the runtime
  provides a managed copy. Pi ships a native binary per platform on its GitHub releases, and the npm
  package `@earendil-works/pi-coding-agent`, which needs Node 22.18 or later.
- **A model route.** In a sandboxed workspace the CLI never holds a model key. It reaches its model
  through the rollout's `inference` connection, which you can pass in `rollout(connections=...)`;
  otherwise `rollout` binds it to the gateway with `HUD_API_KEY` when the agent routes to the gateway
  and the workspace has a network of its own. An agent on its provider key is refused there rather
  than rerouted. Only an unsandboxed workspace (its `ssh` capability declares `isolation="none"`, as
  one without `bwrap` does) gives the CLI its key directly.

### Moving from `openai_compatible` to `pi`

`PiAgent` replaces `OpenAIChatAgent`. The endpoint moves from the config to the environment, and the
request settings keep their names:

| `OpenAIChatConfig` | `PiConfig` |
|--------------------|------------|
| `model` | `model` |
| `base_url`, `api_key` | `OPENAI_BASE_URL`, `OPENAI_API_KEY` in the environment |
| `gateway`, `checkpoint` | `gateway`, `checkpoint` |
| `completion_kwargs` (including `extra_body`) | `completion_kwargs`, merged over Pi's own request fields |
| `system_prompt` | `system_prompt`, appended to Pi's system prompt |
| `max_steps` | `timeout_seconds`, which bounds the whole run; Pi has no step limit |
| `tool_timeout_seconds` | An extension that sets `bash`'s `timeout` (above) |
| none | `extensions`: your own Pi extensions, which add tools and hook Pi's events |
| none | `model_info`: Pi's metadata for the model, such as `contextWindow`, `input: ["text", "image"]` for a vision model, and `compat` for a server's request quirks (for example `{"maxTokensField": "max_tokens"}`) |

Before:

```python
agent = OpenAIChatAgent(OpenAIChatConfig(
    model="my-model",
    base_url="http://localhost:8000/v1",
    api_key="local",
    completion_kwargs={"temperature": 0.2, "extra_body": {"top_k": 20}},
    max_steps=30,
))
```

After, with `OPENAI_BASE_URL=http://localhost:8000/v1` and `OPENAI_API_KEY=local` set:

```python
agent = PiAgent(PiConfig(
    model="my-model",
    completion_kwargs={"temperature": 0.2, "extra_body": {"top_k": 20}},
    timeout_seconds=1800,
))
```

On the command line, `hud eval ... openai_compatible` becomes `hud eval ... pi`, with `base_url` and
`api_key` moved into those variables. Pi runs its own tools (`read`, `bash`, `edit`, `write`) in the
workspace, so it needs an `ssh` workspace; an environment with only MCP tools still needs
`openai_compatible`. Pi reaches only streamable-HTTP MCP servers, where `OpenAIChatAgent` also
reached SSE and websocket ones. Pi records no token ids or logprobs, so training rollouts stay on
`OpenAIChatAgent` (`completion_kwargs` with `return_token_ids` is refused). `stop_on` and
`auto_respond` have no Pi equivalent.

## Create agent

```python
create_agent(model: str, **kwargs) -> GatewayAgent
```

`create_agent` resolves `model` to an agent type and returns that agent routed through the **HUD
gateway**, an OpenAI-compatible endpoint (`settings.hud_gateway_url`, default
`https://inference.hud.ai`) that fronts every provider behind your `HUD_API_KEY`. `model` is either an
agent type (`create_agent("claude_cli")` runs that agent on its config's default model) or any model id
the gateway knows (`claude-...`, `gpt-...`, `gemini-...`; `hud models list` shows them all), which
selects that model's default agent type. To run an agent type on another model, construct the agent
directly with `gateway=True` on its config.

Extra `kwargs` go to the agent's config, with `model` filled in and `gateway=True` set, so the config
stays serializable for [`HostedRuntime`](/v6/reference/runtime#hostedruntime).
`api_key` and `base_url` are rejected.

To call a provider with your own key, construct the agent directly:

```python
from hud.agents import ClaudeCLIAgent
from hud.agents.types import ClaudeCLIConfig

agent = ClaudeCLIAgent(ClaudeCLIConfig(model="claude-sonnet-5-5", timeout_seconds=1800))
```

Constructed directly, an agent uses the provider key when one is set and the gateway otherwise;
`gateway=True` on the config forces the gateway.

### Agent types

An agent type names an agent in `hud eval`, in `create_agent`, and in what `HostedRuntime` sends:

| `AgentType` | Agent now | From hud v0.7.0 |
|-------------|-----------|-----------------|
| `claude_cli` | `ClaudeCLIAgent` | `ClaudeCLIAgent` (alias of `claude`) |
| `codex_cli` | `CodexCLIAgent` | `CodexCLIAgent` (alias of `openai`) |
| `pi` | `PiAgent` | `PiAgent` |
| `claude` | `ClaudeAgent` | `ClaudeCLIAgent` |
| `openai` | `OpenAIAgent` | `CodexCLIAgent` |
| `gemini` | `GeminiAgent` | a Gemini CLI agent |
| `openai_compatible` | `OpenAIChatAgent` | removed; use `pi` |
| `oracle` | `OracleAgent` | `OracleAgent` |
| `nop` | `NopAgent` | `NopAgent` |

### Reference agents

`OracleAgent` and `NopAgent` (`hud.agents`) call no model; they check a task's grading. The oracle
runs one of the task's [reference solutions](#reference-solutions) in an agent's place, so a sound
task passes it. Nop submits nothing and touches nothing, so a sound task fails it. A task without a
reference solution fails the oracle's run before its environment starts.

```bash
hud eval tasks.py oracle --full                        # every task should pass
hud eval tasks.py oracle --config solution=alternate   # run each task's solution named "alternate"
hud eval tasks.py nop --full                           # every task should fail
```

### Reference solutions

A task's reference solutions are its `validation` rows. They travel with the task, locally, in
Docker and on HUD, so an environment needs nothing of its own for the oracle to check it. Each row
is a solution:

| Field | Meaning |
| --- | --- |
| `name` | Names the solution; `OracleAgent(OracleConfig(solution=...))` picks one, else the first runs. |
| `answer` | The answer the oracle submits. |
| `command` | A shell command the oracle runs in the environment's `ssh` workspace as the agent does: as the agent user, from its working directory. Its output and exit code go in the trace; a non-zero exit fails the run. |
| `files` | Files staged under `root` before `command` runs: `path` (relative to `root`), `content`, `encoding` (`utf-8` or `base64`) and `executable`. Up to 1 MiB in all. |
| `root` | Where `files` go: absolute, or relative to the working directory. Defaults to `/solution`; the agent user must be able to create it. |
| `env` | Variables `command` runs with. A `${NAME}` or `${NAME:-default}` value resolves where the oracle runs. |

A solution has a `command`, an `answer`, or both:

```python
task = guess(secret="hunter2")
task.validation = [
    {"name": "reveal", "answer": "hunter2"},
    {"name": "script", "files": [{"path": "solve.sh", "content": SOLVE_SH, "executable": True}],
     "command": "/solution/solve.sh"},
]
```

## Provider agents

<Warning>
The provider agents are deprecated and hud v0.7.0 removes them. Each one warns when it is constructed.
Use `ClaudeCLIAgent` in place of `ClaudeAgent`, `CodexCLIAgent` in place of `OpenAIAgent`, and
`PiAgent` in place of `OpenAIChatAgent`.
</Warning>

A provider agent is HUD's own tool-call loop over one provider's API. Each run it reads the
environment's manifest, opens the capabilities it supports, builds the matching provider tools, and
loops against `run.prompt_messages`.

| Agent | API | Config | Default model |
|-------|-----|--------|---------------|
| `ClaudeAgent` | Anthropic Messages | `ClaudeConfig` | `claude-haiku-5-5` |
| `OpenAIAgent` | OpenAI Responses | `OpenAIConfig` | `gpt-6-luna` |
| `GeminiAgent` | Gemini | `GeminiConfig` | `gemini-3.8-flash` |
| `OpenAIChatAgent` | OpenAI Chat Completions, any compatible server via `base_url` | `OpenAIChatConfig` | `deepseek/deepseek-v4.1-flash` |

Settings specific to these agents:

- **`tool_timeout_seconds`** bounds each SSH-backed tool call, including multi-operation editor calls,
  and returns a timeout to the model as a tool error. Unset by default except on `ClaudeConfig`
  (120 seconds).
- **`ClaudeConfig.reasoning_effort`**: `low`, `medium`, `high`, `xhigh` or `max`, subject to the
  model; sent as `output_config.effort`.
- **`OpenAIConfig.max_output_tokens`** and **`GeminiConfig.max_output_tokens`** are unset by default,
  so each request gets the model's own limit. Gemini counts thinking tokens toward the cap.
- **`OpenAIConfig.prompt_cache_key`** is generated per agent and sent with every request; pass your own
  to share a cached prompt prefix across agent instances.
- **`GeminiConfig.temperature`, `top_p`, `top_k`** are unset by default; Gemini 4 models ignore them.
  **`thinking_level`** accepts `minimal`, `low`, `medium` or `high`, subject to the model (Gemini 4
  Argon rejects `minimal`).
- **`OpenAIChatConfig.completion_kwargs`** pass through to the Chat Completions request.

`GeminiAgent` streams each turn. For Gemini 4 long decode, set `max_output_tokens` above 65,536 and
install `google-genai` 2.30.1 or later; the turn then runs past the per-request output cap and is
recorded as one turn. Otherwise a turn that reaches the cap ends the run with `stop_reason="length"`.
Keep `include_thoughts` on for long-thinking runs: without it the model sends nothing while it thinks,
and a long think can hit the stream's first-chunk deadline.

## Agent

Every agent implements the `Agent` base class (`hud.agents`): one abstract method,
`__call__(run: Run) -> None`. An agent drives the live [`Run`](/v6/reference/types#run) to completion,
filling `run.trace` in place; the graded answer is `run.trace.content`. An agent is stateless per run -
everything comes from `run` - so one instance drives many concurrent rollouts.

Every agent also carries an `AgentConfig` as `agent.config` (`timeout_seconds`, `model`, ...), typed by
its parameter: `Agent[CodexCLIConfig]`. `agent.dump()` serializes that config to JSON and
`AgentClass.load(data)` rebuilds the agent from it; [`HostedRuntime`](/v6/reference/runtime#hostedruntime)
sends the registered agent type plus `dump()`. A subclass that overrides `__init__` calls
`super().__init__(config)`.

## Running an agent

Run a task with an agent two ways. **Programmatically**, pass the agent to `Task.run` or `Taskset.run`
with a [runtime](/v6/reference/runtime):

```python
from hud import Taskset
from hud.agents import create_agent
from hud.runtime import LocalRuntime

agent = create_agent("claude_cli")
taskset = Taskset.from_file("tasks.py")        # scaffolded tasks.py exports a list of tasks
job = await taskset.run(agent, runtime=LocalRuntime("env.py"))
print(job.reward)
```

**From the CLI**, `hud eval` takes a task source and an [agent type](#agent-types); see
[running an eval](/v6/guides/running-an-eval) for the walkthrough and the
[CLI reference](/v6/reference/cli#hud-eval) for the full flag set.

## Bring your own harness

Any loop or framework can be an agent: subclass `Agent`, drive the environment off the `run`, and write
the final answer to `run.trace.content` (what gets graded). Since this is outside the standard workflow,
the seam, the `Run` object you work with, the step types you record, and worked examples live in
[Extending HUD](/v6/advanced/extending#bring-your-own-harness).

To run an agent end to end see [running an eval](/v6/guides/running-an-eval); for where each rollout runs
see [runtimes](/v6/reference/runtime), and for the [`Run`](/v6/reference/types#run) an agent fills see
[types](/v6/reference/types).
