A **runtime** chooses where each rollout's environment runs. You pass it to `task.run` /
`taskset.run` at execution time, and the same task and the same `env.py` run anywhere - only the
runtime changes.

```python
from hud.runtime import LocalRuntime

await taskset.run(agent, runtime=LocalRuntime("env.py"))   # serve env.py locally, run here
```

## Built-in runtimes

| Runtime | Where the env runs | When to reach for it |
|---------|--------------------|----------------------|
| `LocalRuntime("env.py")` | This process, loading your source per rollout | Fastest iteration; local development |
| `SubprocessRuntime("env.py")` | A child process from your source | Local runs isolated from your process |
| `DockerRuntime("my-env")` | A fresh local container per rollout | Reproducibility and parity with production |
| `ModalRuntime("my-env")` | A fresh [Modal](https://modal.com/) sandbox per rollout | Cloud scale, no infra to manage |
| `DaytonaRuntime("my-env")` | A fresh [Daytona](https://www.daytona.io/) sandbox per rollout | Cloud scale on Daytona |
| `Runtime("tcp://host:8765")` | A host you already started | Attaching to a long-lived container or sandbox you own |
| `Shared(inner, width=N)` | One host from `inner` per environment and runtime config, shared by up to N concurrent connections | Multi-agent evals - agents that share, compete, or coordinate over one live environment |
| `HUDRuntime()` | A HUD-hosted env, leased by name and tunneled | Local agent loop against a deployed env |
| `HostedRuntime()` | The whole rollout managed by HUD | Agent and env execute remotely together |

Every runtime imports from `hud.runtime` (`from hud.runtime import LocalRuntime, DockerRuntime,
HUDRuntime, HostedRuntime, ModalRuntime, DaytonaRuntime, Runtime`). Placing a task yourself with
`DockerRuntime` or `ModalRuntime` yields a `DockerEndpoint` (with its `container` id) or a
`ModalEndpoint` (with its `sandbox`), both also in `hud.runtime`.

<Note>
**You can usually omit `runtime=`.** A run without one uses its known placement:

- a platform taskset (`Taskset.from_api`) runs against its deployed environment over the HUD tunnel (`HUDRuntime`), with the agent loop in this process
- a row whose `runtime_config` names an image or Compose project starts it under `DockerRuntime`
- a task created by `@env.template` runs against that environment, in this process

When none of these apply, `run` raises and lists the runtimes you can pass — it never silently picks
one. For example, a JSON row with no image needs `runtime=LocalRuntime(env)` or another runtime.
</Note>

To deploy an environment to the platform and run against it, see
[running an eval](/v6/guides/running-an-eval) and
[deploying to the platform](/v6/guides/creating-an-environment#deploying-to-the-platform).

## RuntimeConfig

`RuntimeConfig` carries the typed construction input a container-based runtime needs: an image or
Compose project, hardware, and timeouts. Set it on the runtime (`runtime_config=`) or per row on
[`Task.runtime_config`](/v6/reference/tasks#task); the runtime merges the two and applies what it
supports.

```python
from hud.runtime import (
    ComposeProject,
    RuntimeConfig,
    RuntimeGPU,
    RuntimeLimits,
    RuntimeResources,
    RuntimeTPU,
)

RuntimeConfig(
    image="my-env",
    resources=RuntimeResources(
        cpu=4,
        memory_mb=8192,
        storage_mb=32768,
        gpu=RuntimeGPU(type=["H100", "A100"], count=1),
    ),
    limits=RuntimeLimits(startup_timeout_s=300, run_timeout_s=1800),
)

RuntimeConfig(compose=ComposeProject(document="./compose.yaml"))
RuntimeConfig(resources=RuntimeResources(tpu=RuntimeTPU(type="v5", topology="2x2")))
```

| Field | Description |
|-------|-------------|
| `image` | Image to run. |
| `compose` | `ComposeProject(document, root, service_access)`. Mutually exclusive with `image`. |
| `resources` | Placement requests: CPU, memory, disk, acceptable GPU types and count, OS, or TPU slice. |
| `limits` | `RuntimeLimits(startup_timeout_s, run_timeout_s)`. |

Support differs per runtime. Providers reject unsupported requirements except `storage_mb`, which
is best effort: `DockerRuntime` admits against available disk and `DaytonaRuntime` provisions
enough whole GiB, while providers without disk sizing proceed with their default capacity.
`HUDRuntime` proceeds on the deployed environment's defaults and warns when it ignores CPU, memory,
or storage requirements; it rejects GPU, OS, TPU, and `limits`. Daytona accepts a list of GPU
alternatives; Modal accepts one GPU type. Daytona rejects Compose, `run_timeout_s`, and resource overrides
when booting from an already-built snapshot. `LocalRuntime` rejects a
per-task `runtime_config`.

`run_timeout_s` bounds the lifetime of the provisioned environment, not the complete rollout.
Without one, `DockerRuntime` sets no lifetime bound, while `ModalRuntime` and HUD-hosted Modal
rollouts allow the task's agent timeout (`agent_config.timeout_seconds`) plus 3600 seconds for
startup, grading, and teardown.
The optional `rollout_timeout` passed to `Task.run` or `Taskset.run` is the execution deadline
through grading, including submission, queueing, and provisioning. It is not an upper bound on
method-return latency: cancellation and trace reporting still run after expiry, and `Taskset.run`
then flushes telemetry. When both are set, `run_timeout_s` and other known phase limits must be less
than `rollout_timeout`; an agent timeout must also be less than the actor environment's
`run_timeout_s`. Contradictory values fail before execution. When `rollout_timeout` is omitted, the
SDK adds no overall deadline; configured phase limits and limits imposed by the selected runtime
still apply.

When the SDK owns the environment process, its output is part of the local eval:
`SubprocessRuntime`, Docker image and Compose runtimes, Modal image and Compose sandboxes,
and Daytona sandboxes stream stdout and stderr directly to the terminal without
reformatting them. `LocalRuntime` already shares the eval process's terminal. HUD-hosted
runtimes retain environment output on the hosted trace instead.

## Runtime directory

The constructor for each built-in runtime:

### `LocalRuntime`

```python
LocalRuntime(source, *, env=None, ready_timeout=120.0)
```

Runs an environment in the current Python process. `source` can be:

- **A `.py` file or directory:** load the environment from that source.
- **An `Environment`:** reuse that instance.
- **A `(task) -> Environment` function:** call it for each rollout.

`env` selects an environment by name when loading a source; it defaults to the task's
environment. `ready_timeout` limits how long initialization can take.

Rollouts using the same environment instance run one at a time, including when a
source or function returns a cached instance. Distinct instances can run concurrently.

Imported modules share state between runs. Loading a second copy of a package from
another directory, or a source whose sibling modules (such as its `env.py`) another
directory's source already imported, raises an error. Use `SubprocessRuntime` for
separate Python processes.

### `SubprocessRuntime`

```python
SubprocessRuntime(source, *, env=None, ready_timeout=120.0)
```

Starts a new process for each rollout and stops it afterward.

- **`source`** - a `.py` file or directory exporting environments or tasks created by
  `@env.template`. The source must import all templates and hooks needed for the run.
- **`env`** - the environment name to serve. Defaults to the task's environment.
- **`ready_timeout`** - seconds to wait for the process to start serving.

You can also pass an `Environment` whose templates all live in one file; the runtime
serves that file. Each process runs from its source directory and shares host files
and ports.

### `DockerRuntime`

```python
DockerRuntime(image=None, *, port=8765, run_args=(), bind_mounts=(), compose_service_socket=None, runtime_config=None, env_vars=None)
```

- **`image`** - image name to run; shorthand for `runtime_config.image`.
- **`port`** - port the image's CMD serves inside the container (the scaffolded `Dockerfile.hud` serves `8765`).
- **`run_args`** - extra `docker run` flags, e.g. `["--gpus", "all"]` or `["-e", "KEY=VAL"]`. Image environments only.
- **`bind_mounts`** - `DockerBindMount(source, target, read_only=True)` host paths to mount into the environment (the `main` service of a Compose environment).
- **`compose_service_socket`** - the host Docker socket to hand a Compose environment that declares `service_access`. Defaults to the local daemon's socket; required when the daemon is remote.
- **`runtime_config`** - a `RuntimeConfig` (image or Compose file, resources) for finer control.
- **`env_vars`** - environment variables set in the environment (the `main` service of a Compose environment).

For Compose environments, the service named `main` must serve HUD's control
channel on `port`. `DockerRuntime` starts the project and publishes that
service's control port. Constructor-level `image` is shorthand for
`runtime_config.image`. Project structure, build hooks, the private Docker
daemon, and the security override are documented in
[Compose environments](/v6/experimental/compose#runtime-behavior).

### `ModalRuntime`

```python
ModalRuntime(image_name=None, *, image=None, command=None, app=None, app_name=None, workdir=None, port=8765, runtime_config=None, env_vars=None, sandbox_secrets=None, registry_secret=None, region=None, tags=None, volumes=None)
```

- **`image_name`** - published Modal image name (the preferred durable handle), e.g. `ModalRuntime("hud-libero-env")`.
- **`image`** - an `Image` to build lazily on first use, as an escape hatch.
- **`command`** - override the serving command (defaults to the scaffolded `hud serve` entrypoint).
- **`workdir`** - working directory inside the sandbox. Left unset, Modal keeps the image's `WORKDIR`.
- **`app`** - an already-running, caller-owned Modal app. `ModalRuntime` does not manage its lifecycle.
- **`app_name`** - a Modal app to look up. Defaults to `hud-envs` when `app` is not supplied; `app` and `app_name` are mutually exclusive.
- **`port`** / **`env_vars`** - in-sandbox serving port and extra environment variables.
- **`sandbox_secrets`** - Modal `Secret` objects to attach to the environment's container. Resolve named secrets with `modal.Secret.from_name(...)`; their values never pass through the local process.
- **`registry_secret`** - optional Modal `Secret` for pulling private registry images (`REGISTRY_USERNAME` / `REGISTRY_PASSWORD`), for the environment and for Compose services. Unused for `modal://` images.
- **`region`** - the Modal region every sandbox runs in. Defaults to `MODAL_REGION`, so a caller that itself runs on Modal keeps its environments beside it; unset elsewhere, Modal places them.
- **`tags`** - Modal tags set on every sandbox, for `Sandbox.list(tags=...)`.
- **`volumes`** - Modal `Volume`s mounted in the environment's container by path, e.g. `{"/agents": modal.Volume.from_name("agent-bundles").read_only()}`.

<Accordion title="Running a private Docker image">

```python
import modal
from hud.runtime import ModalRuntime, RuntimeConfig

ModalRuntime(
    runtime_config=RuntimeConfig(image="ghcr.io/org/private:tag"),
    registry_secret=modal.Secret.from_name("registry-creds"),
    sandbox_secrets=[modal.Secret.from_name("hf-token")],
)
```

</Accordion>

The environment is the sandbox's main container, where a requested GPU attaches. Declared
`cpu` and `memory_mb` are hard limits: an environment that exceeds its memory ends the sandbox
with exit code 137, which the run's error reports. The control channel is reached through a
connect-token WebSocket on the sandbox; a fresh token is minted for every connection.

For Compose input, every service runs in the one sandbox: `main` is its main container and each
other service a sidecar, reached by service name. The runtime starts every service, `main`
included, once what it `depends_on` is up, honoring `service_started`, `service_healthy` and
`service_completed_successfully` by running the declared healthchecks itself; like
`docker compose up --wait`, every healthchecked service, `main`'s own included, is healthy before
the environment is handed to the rollout. `restart` policies apply to sidecars. Service images
must be pre-built: a registry reference or `modal://<image id>`; a service with only a `build` is
refused, as are `network_mode`, `user`, a service waiting for `main` to complete, a GPU on any
service but `main`, and a GPU together with `service_access`. With `service_access`, the sandbox
runs on Modal's VM runtime with a Docker daemon sidecar at `DOCKER_HOST` (reserving 1 GiB); that
runtime sizes every container, so `resources.memory_mb` and a `mem_limit` on every other service
are required, it is CPU-only, and it is the one whose root checkpoints are faithful. Sidecar
output is not streamed; `exec` reaches a sidecar by name. `env_vars` and `sandbox_secrets`
apply to `main`.

Requires the `modal` extra (pinned to one Modal client release) and a configured token.

### `DaytonaRuntime`

```python
DaytonaRuntime(snapshot_name=None, *, image=None, command=None, workdir="/app", port=8765, ssh_host="ssh.app.daytona.io", ssh_expires_minutes=1440, runtime_config=None)
```

- **`snapshot_name`** - Daytona snapshot to boot from (the durable handle).
- **`image`** - Dockerfile/registry ref to build the snapshot if it's missing. Daytona records what a snapshot was built from, so when the image content changes (an edited Dockerfile or context file, a repointed registry ref) the snapshot is rebuilt in place under the same name instead of silently reusing the build from before the edit.
- **`workdir`** / **`port`** - guest working directory and in-sandbox serving port.
- **`ssh_host`** / **`ssh_expires_minutes`** - SSH tunnel settings (Daytona exposes services over an SSH local-forward).

Resources (cpu/memory/gpu) are fixed on the snapshot at build time. With `image`, a task's `runtime_config.resources` builds a sized variant under a suffixed name (`my-env-4cpu`); without `image`, an already-built snapshot cannot be resized.

`DaytonaRuntime` does not run Compose projects: a `runtime_config.compose` is rejected. Use
`DockerRuntime` or `ModalRuntime` for [Compose environments](/v6/experimental/compose).

Measured behavior at scale, up to 256 concurrent sandboxes with warm pools, is written up in the [Daytona cookbook](/v6/cookbooks/daytona-rl) and the [full guide on Daytona's docs](https://www.daytona.io/docs/guides/reinforcement-learning/hud-rl-cookbook).

### `HUDRuntime`

```python
HUDRuntime(*, runtime_url=None)
```

- **`runtime_url`** - override the runtime endpoint the tunnel connects to.

The SDK leases your deployed env by name and tunnels to its control channel; the agent loop runs local.

### `HostedRuntime`

```python
HostedRuntime(*, poll_interval=5.0)
```

- **`poll_interval`** - seconds between trace-status polls while the rollout runs remotely.

For example, a task with `RuntimeLimits(run_timeout_s=18_000)` can omit `rollout_timeout` to avoid
adding an SDK-wide cap. To add one, pass a larger value such as
`task.run(agent, runtime=HostedRuntime(), rollout_timeout=18_600)`, leaving time for queueing and
provisioning.

Where `HUDRuntime` runs the agent loop locally against a tunneled env, `HostedRuntime` runs the
**whole rollout** remotely, with the agent running alongside the task environment. This process
only submits the rollout and polls its trace to completion. It supports registered built-in agents;
[`create_agent`](/v6/reference/agents#create-agent) supplies the gateway-backed ones. Agents with a
custom `model_client` must use `HUDRuntime` or `LocalRuntime`.

### `Runtime`

```python
Runtime(url, params=..., config=...)
```

- **`url`** - control-channel address of an already-running host: `tcp://host:8765`, `tls://host:443` (the same stream inside TLS), or `ws://` / `wss://` (a WebSocket whose binary messages carry it). A WebSocket address sends `params["headers"]` with its handshake.
- **`params`** - connection-time data a transport may need (auth token, sandbox id).

### Filesystem interface

A runtime a provider yielded also owns the box's filesystem. `DockerRuntime` and `ModalRuntime`
implement these on their endpoint; a `Runtime(url)` you constructed, `LocalRuntime`,
`SubprocessRuntime`, `HUDRuntime` and `DaytonaRuntime` raise `RuntimeUnsupportedError` (with
`.runtime`, `.operation` and `.reason`) instead of approximating them.

```python
from hud.runtime import RootScope, SessionScope, WorkspaceScope

result = await box.exec(["sh", "-c", "redis-cli save"], service="redis")   # ExecResult
copies = await box.collect(["/data/dump.rdb", "/logs"], tmp_dir, service="redis")
async with box.checkpoint(WorkspaceScope("/work")) as work:
    await other.restore(work, WorkspaceScope("/work"))
async with box.checkpoint(RootScope()) as image:
    await task.run(agent, runtime=provider_for(RuntimeConfig(image=image.ref)))
```

| Operation | What it does |
|-----------|--------------|
| `exec(argv, *, service="main", max_wait=None)` | Runs a command in the environment, or in a sibling Compose service, and returns its `returncode`, `stdout` and `stderr`. A command still running after `max_wait` seconds is stopped and the call raises `TimeoutError`. |
| `collect(paths, destination, *, service="main")` | Copies files and directories out of the box into `destination` (each at `destination / path.name`); a link to an absolute path or outside `destination` is rejected. |
| `checkpoint(scope)` | Captures a `SessionScope(session_id)`, a `WorkspaceScope(path)` or the `RootScope()` for the duration of the `async with`. Session and workspace checkpoints are archives of regular files and directories; a root checkpoint is an image the same provider boots from `runtime_config.image`. |
| `restore(checkpoint, scope)` | Replaces a session or workspace in a running box with a checkpoint of the same kind (`ValueError` otherwise). A root checkpoint is restored by starting a new box from it. |
| `terminated()` | Why the box stopped (its exit code, and whether the memory limit killed it), or `None` while it runs. A rollout that fails while the box is held adds this to the recorded error. |

`transports_sessions` says whether a runtime moves control sessions this way. A rollout whose
verifier declares its own `runtime_config` in the actor's environment gets its own box only on
such a runtime; elsewhere the verifier runs beside the actor and a warning says so. Modal declines
root checkpoints on its default runtime, whose filesystem snapshots do not preserve file modes.

### `Shared`

```python
Shared(inner, *, width)
```

- **`inner`** - the `Provider` that boots each shared host, e.g. `DockerRuntime("my-env")`.
- **`width`** - how many concurrent connections each host accepts.

A lease pool with one host per environment and runtime config: a host boots through `inner` on the
first lease for its key and lives for the enclosing `async with` scope, or until its run timeout,
when the next lease boots a fresh one. Every rollout of one environment and config in that scope is
handed the same address - agents
that need to share, compete, or coordinate in the same environment (a vectorized sim's `num_envs`
slots, see [robots](/v6/advanced/robots#vectorized-envs-and-evals), are one case). Lease
`width + 1` waits for a slot to free instead of erroring, so `group` and `max_concurrent` keep
their ordinary meanings. `Taskset.run` scopes a context-manager placement to the call, so a bare
`runtime=Shared(...)` boots once per `run(...)`; open the scope yourself to keep the host
warm across several calls:

```python
async with Shared(DockerRuntime("hud-isaac-env"), width=8) as rt:
    await taskset.run(agent, runtime=rt, group=8)
    await taskset.run(agent, runtime=rt, group=8)  # same live sim
```

`Runtime(url)` needs no wrapping since every caller already dials the same address.

## Run on your own infra

A **runtime is just a function**: given a task, start a container somewhere and yield its
control-channel URL. That one function is the whole integration surface for any provider - Modal, E2B,
Runloop, your own Kubernetes:

```python run.py
from contextlib import asynccontextmanager
from hud.runtime import Runtime

@asynccontextmanager
async def my_runtime(task):
    sandbox = await start_my_sandbox(image="my-env")   # your infra brings it up
    try:
        yield Runtime(f"tcp://{sandbox.host}:{sandbox.port}")
    finally:
        await sandbox.terminate()                       # ...and tears it down

await taskset.run(agent, runtime=my_runtime)
```

`DockerRuntime` and the rest are just built-in versions of this. Anything that starts your image and
hands back a URL plugs in with no change to the environment or the task - that's what "run anywhere"
means concretely. Constructed directly, `Runtime(url)` yields itself with a no-op lifecycle, since
whoever provisioned the host owns teardown.

Placement can also vary per task: a runtime is called once per rollout with the task row being placed,
so one callable can route heavier rows to heavier hosts.

A failure your runtime can name travels with its name. Raise `hud.types.ClassifiedError` (or a
subclass) with a `code` and a `source` of `user`, `platform` or `provider`, while placing the box
or from code that runs mid-rollout, and the run records them as `trace.error_code` and
`trace.error_source`, which the trace exit reports; an unclassified exception ends the run the
same way without them.
